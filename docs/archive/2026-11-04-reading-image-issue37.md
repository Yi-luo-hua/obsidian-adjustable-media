## 继续定位所需信息

### 附件覆盖与缓存差异：已复现的候选场景

同一环境、同一 0.9.3 构建，另建临时笔记与临时 PNG，不改原有附件：

1. 用正常 PNG 打开实时预览，两张布局图片的 `naturalWidth` 均为 800。
2. 经 `vault.modifyBinary` 将该临时附件替换成 4 字节无效内容，模拟附件在同步或图片处理过程中暂时不可解码。编辑视图保留已加载的图片，两张 `naturalWidth` 仍为 800，地址仍携带旧修改时间。
3. 切换阅读模式。新建图片使用附件的新修改时间 URL，两张 `naturalWidth` 均为 0，出现破图。
4. 将附件恢复成原正常 PNG，等待 500ms 后当前阅读页仍保留失败地址，`naturalWidth` 仍为 0。

另一次先在阅读模式加载无效附件、再恢复附件的检查同样不会自动恢复；重新切换模式后图片恢复，强制 `previewMode.rerender(true)` 后也能正常显示。

这确认了一个条件性缺口：`layoutView.ts` 直接设置资源 URL；`viewEnvironment.ts` 捕获图片错误后只触发布局测量；`readingView.ts` 的文件事件按笔记文件身份核对，普通图片内容修改不会使引用它的阅读布局重新解析 URL。编辑与阅读共用渲染器，也仍可能因创建时间和缓存不同而显示不同结果。

本次没有实际运行同步或图片压缩插件，因此“云同步未完成”“第三方工具覆盖附件”只是可能触发该时序的假设，不能当作报告者环境的事实。应询问破图是否会在重新打开笔记后恢复，以及是否使用同步、按需下载或自动图片处理。若只是附件尚未出现，解析器还可能显示“找不到：…”；本次复现特意保留已被索引的文件，改变其内容。

两轮补充检查结束后已移除临时附件与笔记，再次核对 124 篇原有 Markdown 笔记和 4 份原插件文件，哈希均不变。

### 其他候选与区分方法

- 阅读后处理器冲突：其他插件可在阅读模式改动图片 DOM。比较两种模式的 `src`、`srcset`、`data-src` 与资源加载错误，检查是否在本插件渲染后发生修改；在只保留本插件的测试副本中对照。尚未发现具体冲突插件。
- 宿主／插件版本差异：本轮只覆盖 Obsidian 1.15.0 与本仓库 0.9.3 构建，不能据此排除报告者版本上的资源协议或后处理顺序问题。
- 纯尺寸／普通 CSS 隐藏的优先级较低：截图已有破图标记和替代文本，首先应检查资源是否加载；如 `naturalWidth > 0`，再转查显示样式。CSS 修改 `content` 等特殊情况仍需实际样式才能判断。

### 原始复现信息

请报告者提供：

1. 出问题布局的完整 Markdown（包括前后 `<!-- vml … -->` 注释和图片嵌入行），以及笔记与附件在库内的相对路径。
2. Obsidian 与 Adjustable Media 版本、操作系统、主题名称和启用的 CSS 片段。
3. 将同一图片原样复制到布局外后，阅读模式是否仍然破图。

若布局外正常，进一步比较两处图片的实际 `src` 与加载错误；若布局外也破图，先检查宿主的附件路径和资源加载。拿到最小复现后再确定修复位置。
